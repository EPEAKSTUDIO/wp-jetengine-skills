Full audit of skill coverage vs. the actual plugin source in `plugins/` and the live
JetEngine MCP server on `jackfruit.epeak.studio`. Goal: find what's missing, verify one
high-value gap end-to-end, and leave a prioritized backlog for what's left.

## Open Skills / Agent Skills standard compliance

ecosystem is built on **Anthropic's open Agent Skills format**, specified at

| `description`: 1–1024 chars | **Pass** — longest is 535 chars (`jetengine-cct-internals`) |
| Body ≤500 lines (recommended) | **Pass** — longest is 151 lines |
| `license`/`metadata` field shapes (metadata = string→string map) | **Pass** |
| Directory structure (`scripts/`, `references/`, `assets/` optional) | N/A — no skill here uses these yet; all detail lives directly in `SKILL.md` + `TEST-REGIMEN.md`, which is allowed but not the spec's suggested "push detail to references/" pattern |

No changes needed for compliance. One low-cost improvement available but not applied:
the optional `compatibility` field (max 500 chars, "environment requirements") isn't set
on any skill — could add something like `compatibility: Requires shell/file access to
WordPress plugin source and a WP REST-capable sandbox for live verification` to flag that
these skills assume filesystem + HTTP access, not just chat. Left as a backlog item since
"most skills do not need it" per the spec itself.

## Gap analysis by plugin (source directories with no skill coverage)

### JetEngine (`plugins/jet-engine/includes/`) — largest gap surface

Covered: `components/{relations,listings,query-builder{mcp only}}`,
`modules/custom-content-types` (partial, read-side only), `core/mcp-tools`.

**Not covered, roughly by priority (developer-facing impact, not just size):**

1. **Query Builder itself** (`components/query-builder/` minus the `mcp/` subfolder) —
   the 10 real `sql`/`posts` queries live on jackfruit prove this is core to how
   JetEngine sites actually expose data to REST/automations (Make/Integromat-style
   `api_endpoint: true` queries with `api_namespace`/`api_path`/`api_schema`). No skill
   documents: the `%query_var|x%` / `%query_results|N|ids|field%` dynamic-arg macro
   syntax seen live in every query's `__dynamic_sql`/`__dynamic_posts` block, how
   `avoid_duplicates` / `cache_query` / `cache_expires` work, or how a query becomes a
   public REST endpoint (`api_access: 'role'|...`, `api_access_cap`). **Highest-value
   next skill** — there's a `jetengine-query-builder` gap directly adjacent to the new
   `jetengine-mcp-tools` skill and easy to verify against the 10 live queries already
   on the sandbox.
2. **Options Pages, Meta Boxes admin-UI internals (write side)** — `cct-internals`
   only covers *reading* CCT/relation data; nothing covers building meta boxes/options
   pages by hand (as opposed to via the new MCP tool). Now partially bridged by
   `jetengine-mcp-tools`, but raw-PHP registration (`Jet_Engine_Meta_Boxes`) is untouched.
3. **JetEngine's own REST API** (`includes/rest-api/`, `modules/rest-api-listings`) —
   distinct from the *custom* endpoints built in `cct-internals`; this is the
   plugin's built-in default CPT/CCT REST exposure and the "Rest API Listings" module
   (consuming *external* REST APIs as a listing source, plus its Woo-notification
   feature) — neither traced.
4. **Dynamic Visibility** (`modules/dynamic-visibility`) — Elementor/Bricks widget
   conditional-display rules keyed off meta/role/query. Common source of "why is this
   widget hidden" bug reports.
5. **Data Stores** (`modules/data-stores`) — wishlist/favorites/bookmark storage API,
   commonly chained with front-end forms.
6. **Profile Builder, Calendar, Maps Listings, QR Code, Gallery modules** — smaller,
   more self-contained integrations; lower priority unless a specific task needs one.
7. **Legacy "Forms (Legacy)" module** (`modules/forms`) — deprecated per JetEngine's own
   module description ("would be updated only for critical bug fixes... proceed to
   JetFormBuilder") — deliberately **not** recommending a skill here; `jetformbuilder-*`
   already covers the maintained path.
8. **Glossaries** (`components/glossaries`) — now partially covered by
   `jetengine-mcp-tools` (the `tool-add-glossary` MCP tool), but the "smart" (non-manual)
   glossary sources (post-type-as-glossary, taxonomy-as-glossary, etc. — `data.php`) are
   untouched; the MCP tool only supports `source: manual`.

### JetFormBuilder (`plugins/jetformbuilder/`)

Covered: `includes/actions/` (custom action classes), the core submission lifecycle

**Not covered:**

3. **Payment/webhook integrations** (`modules/gateways`, `modules/multi-gateway`,

5. **JetFormBuilder's own REST API** (`modules/rest-api`) — untouched; unclear if forms

### JetSmartFilters (`plugins/jet-smart-filters/`)

Covered: the checkbox-filter→query pipeline, AJAX endpoint, custom filter-type/provider
registration. The existing `jetsmartfilters-query` skill **already flags its own gaps**
in its "Gotchas"/closing section:

1. `includes/indexer/` — the opt-in performance layer, its DB table shape, and how
   filter option counts get pre-computed. Explicitly called out as "not traced" already.
2. `includes/plain-query/`, `includes/tax-query/` — URL query-var / dynamic-var handling.
3. `includes/compatibility/*` — WooCommerce, WPML, RankMath, Weglot patch files;

4. Elementor/Bricks-specific filter/provider render paths (`includes/elementor/`,
   `includes/bricks/`) — the base pipeline is documented, builder-specific wiring isn't.

These four are lower priority than the JetEngine gaps above since the existing skill
already scopes them honestly as open questions rather than silent gaps.

## Follow-up round: the write-side API gap (same day, second pass)

The user flagged the actual motivating problem for this whole repo: agents hallucinating
JetEngine function names for **creating relations, updating relations, and updating CCT
data** — precisely the write side, which the first pass of this audit hadn't covered
(everything shipped so far, including `jetengine-cct-internals` and `jetengine-relations`,
was read-only: `get_parents`/`get_children`, raw `$wpdb` reads). Traced and live-verified
the real write APIs, which did not exist in any skill before this:

- **CCT row CRUD**: `Item_Handler::update_item( $itemarr )` (insert if no `_ID` key,
  update if present, one method for both) and `Item_Handler::raw_delete_item( $id )`
  — obtained via `Module::instance()->manager->get_content_types( $slug )->get_item_handler()`.
  Added to `jetengine-cct-internals` (which also gained its first `TEST-REGIMEN.md`).
- **Relation link CRUD**: `Relation::update( $parent_id, $child_id )` (create or move a
  link, idempotent, auto-creates the main DB table on first use) and
  `Relation::delete_rows( $parent_id, $child_id )` (remove a link). Added to
  `jetengine-relations`.
- **A real, previously-unknown gotcha**: `Relation::update_meta()`/`delete_meta()`
  write to a *separate* per-relation `_meta` table that, unlike the main link table,
  is **not** auto-created — calling `update_meta()` on a relation that's never had a
  meta table created silently no-ops (no error, `get_meta()` just returns `false`
  forever after). Confirmed live via direct `SHOW TABLES` check. This is exactly the
  kind of "looks right, silently doesn't work" trap that causes agents to write code
  that appears to succeed but doesn't.

All of this was live-verified, not just source-read: created a real CCT row (insert +
update + delete), a real relation (id 17, created via the same internal `Data` CRUD the
admin UI and MCP tools use — no admin UI or MCP relation tool needed), linked/unlinked
it, and reproduced the meta-table gotcha on purpose. Two more probe snippets (ids 20, 21)
kept and documented per the same convention as before.

This also **unblocked** the `jetengine-relations` `TEST-REGIMEN.md`, which had been
stuck since 2026-07-15 on "no relation exists on this site and no MCP tool creates one" —
turns out a relation doesn't need the admin UI or an MCP tool either, same as CCT/CPT/
taxonomy: the internal `Data::create_item(false)` CRUD works directly.

**Remaining known write-side gaps** (not yet covered, candidates for next pass):
CPT/taxonomy row-level writes (`wp_insert_post`/`wp_update_post` themselves are core WP,
not JetEngine-specific, so likely lower priority — but JetEngine's own meta-box field
read/write helpers for CPTs, if any exist beyond core `get_post_meta`, weren't checked),
and whether there's a JetEngine-level "set_field_value" abstraction that other Crocoblock
plugins call instead of raw meta functions (unconfirmed either way — worth a targeted
grep for `jet_engine()->meta_boxes` field-value helpers in a future pass, since that's
exactly the shape of function an agent might guess wrong).

## Third round: full developer-facing API surface across all three plugins (same day)

The user asked the broader question directly: "in terms of PHP functions available for
developers... do we cover the entire range of what's possible?" — not just the
CRUD-shaped gaps from round two, but everything a developer could leverage writing
custom code on top of JetEngine, JetFormBuilder, and JetSmartFilters.

Ran three parallel source inventories (one per plugin, full read of
`plugins/{jet-engine,jetformbuilder,jet-smart-filters}/`) specifically hunting for
developer-facing subsystems with no skill coverage at all. Found and closed:

**JetEngine** (new skills `jetengine-query-builder`, `jetengine-modules`):
- Query Builder (`Query_Factory`, `Manager::get_query_by_id()`, custom query-type
  registration) — this was backlog item #2 from round two, now done.
- Meta Boxes (`register_metabox()`, `get_fields_for_context()` — and the "must be
  called at `init` priority ≥ 11 or returns empty" silent-failure trap).
- Options Pages (no `jet_engine_get_option()` helper exists — real path is
  `registered_pages[$slug]->get()`; storage mode determines whether core
  `get_option()` even sees the value).
- Data Stores (favorites/recently-viewed lists — NOT a generic key-value API, a
  common misreading of the module name).
- Dynamic Visibility (standalone module, not part of JFB/JSF as agents often assume;
  `Condition_Checker::check_cond()` as the callable-standalone entry point).
- Glossaries, Custom Meta Tables (per-field custom-table storage, distinct from CCT —
  `get_post_meta()` silently misses data stored this way).
- Noted but not yet turned into a skill: JetEngine's own Booking Forms/Calendar module
  (`Jet_Engine_Booking_Forms`) — distinct from JetFormBuilder, easy to confuse by name;
  and the Dynamic Functions registry (Elementor dynamic-tag data resolvers, separate
  from the `%macro%` system in `jetengine-listings-macros`).

**JetFormBuilder** (new skill `jetformbuilder-fields`):
- `jet_fb_context()`/`Parser_Context` — flagged by the research pass as the single
  most load-bearing gap: the generic accessor for reading/writing a submitted field's
  value, used identically inside custom actions and Call Hook callbacks, that neither
  `jetformbuilder-actions` nor `jetformbuilder-hooks` documented.
- Repeater fields resolve via **dotted path** (`repeater.0.field`), not bracket
  array-index syntax — a concrete, easy-to-get-wrong detail.
- Custom field block type registration (`jet-form-builder/blocks/register` action +
  repository pattern, not a filter) and the separate field-parser registration that's
  easy to conflate with it.
- **A genuine negative finding**: there is no public filter to register a custom
  validation rule class (`Rules_Controller::rep_instances()` hardcodes the list, no
  `apply_filters`) — an agent asked for this will very likely hallucinate a
  `jet-form-builder/register-validation-rule`-style filter that doesn't exist.
- Presets vs. plain default values (two different mechanisms, Preset + Source split).
- Form Records live in custom DB tables via `Query_Builder`/`Base_Db_Model`, not
  `wp_posts` — and **there is no REST route for submission itself** (classic
  AJAX/`wp_loaded`, not `register_rest_route()`), another common wrong assumption.
- Noted but not yet turned into a skill: the Payment Gateways module (base gateway
  action, PayPal API actions, DB-backed payment records).

**JetSmartFilters** (extended the existing `jetsmartfilters-query` skill in place,
closing the "not yet traced" note it already carried):
- The indexer's read/write split (`Indexer_Manager` write-side vs. `Indexer_Data`
  read-side — different classes, unrelated method names, easy to assume one class).
- JetSmartFilters has its **own standalone Listing/Query-Builder engine** with its own
  DB-backed storage, entirely separate from JetEngine's Listing Grid (different
  plugin, different table) — a genuinely easy thing to miss entirely.
- The Provider Helpers registry (`->providers->helpers->{integration}` magic-getter,
  not static calls).
- Tax-query/plain-query dynamic-var resolution is a **two-file mini-system per query
  type**, resolved separately at render time vs. indexer time — a custom dynamic var
  registered only in the render-time hook silently leaves indexed data stale.
- `Service_Filters` as a direct-PHP-callable CRUD escape hatch around the admin-only
  REST namespace.
- The hierarchical term `Walker` as a bespoke rendering path separate from the normal
  filter-type pipeline.

None of round three's new claims are live-verified yet (source-cited only, each new
skill's `TEST-REGIMEN.md` says so explicitly) — JetSmartFilters in particular is not
even installed on the only sandbox available this session (confirmed dead end,
documented in that skill's regimen since 2026-07-15), so its tests stay blocked until
a site with the plugin is available.

## Fourth round: a runnable test-suite harness, replacing one-off probe snippets

The user asked for something more durable than the per-investigation throwaway
snippets used in rounds one-three: a reusable, machine-checkable test suite per skill
that a future auditing agent can just run, instead of re-deriving probe code from
scratch — and one that makes it obvious whether a failure means "the plugin changed"
or "this test has a bug." Also: JetSmartFilters got installed on the sandbox this
round, unblocking that skill's regimen for the first time.

Built and documented the convention in `docs/test-harness-guide.md`:
`test-harness/core-snippet.php` (deploy once, permanently active — `agent_test_assert()`/
`agent_test_run_suite()` plus `GET /agent-test/v1/suite/{suite}` and `/suites` REST
routes) plus one `tests.php` per skill, deployed as its own snippet, each assertion
recording `{id, claim, pass, expected, actual, notes}` with a file:line citation.

**Proved it out live on two skills — and it immediately paid for itself**, catching
three real documentation bugs from round three that source-reading alone had missed:

- `jetengine-query-builder`: the documented `jet_engine()->query_builder->manager`
  accessor **does not exist anywhere in the plugin** — first suite run failed all 4
  assertions with "call to a member function on null." Real API is the static
  singleton `Jet_Engine\Query_Builder\Manager::instance()`; `Query_Factory::register_query()`
  is a static method, not an instance call; the registration hook fires with a class
  name string, not an object. All fixed, suite now 4/4 pass, plus two bonus confirmed
  facts (bogus id returns `false`, and JetEngine's own other modules register three
  more query types beyond the eight documented core ones).
- `jetsmartfilters-query`: `jet_smart_filters()->providers->helpers` — wrong, no such
  property on the providers manager; the real path is
  `get_providers('jet-engine')->helpers` (a lazy `__get()` on the provider instance).
  `jet_smart_filters()->indexer->data` is genuinely `null` when the indexer is
  disabled (default) — the original test wrongly required it to always be an object.
  **And a real plugin landmine, not a documentation bug**: directly instantiating
  `new \Jet_Smart_Filters\Listing\Storage\Controller()` **crashes the entire site**
  (uncatchable "Cannot redeclare class" fatal) because the top-level
  `Listing\Controller::instance()` singleton already creates one on WP `init`, and
  `Storage\Controller`'s constructor does a raw `require` (not `require_once`). Fixed
  by using `Listing\Controller::instance()->storage` instead. All 5/5 pass now.

Both suites, plus the shared harness, are deployed and kept on the sandbox (snippet
ids 22-24; two throwaway isolation-diagnostic snippets, 25-26, kept deactivated per
this repo's keep-don't-delete convention — 25 in particular reproduces the crash on
purpose and must not be activated/hit casually).

## Sixth round: tests.php for the last 6 pre-harness skills — harness coverage complete (same day)

Closed out backlog item 2 fully: `jetengine-cct-internals` (3/3), `jetengine-relations`
(6/6), `jetengine-mcp-tools` (4/4), `jetengine-listings-macros` (5/5),
`jetformbuilder-actions` (3/3), and `jetformbuilder-hooks` (3/3) all got runnable
`tests.php` suites, deployed as Code Snippets ids 29-34. **Every domain skill in this repo
now has a runnable suite** — 46/46 assertions passing across all 10 suites.

No live plugin bugs turned up this round either, but two real documentation additions
were found (not corrections — both prior claims stayed correct, just incomplete):
`tool-add-query`'s stored `order`/`args` rows carry undocumented `_id`/`collapsed`/`type`
keys (`jetengine-mcp-tools` mcp-4), and pipe-arg macro syntax (`%macro|foo,bar%`) is
silently dropped unless the macro class declares a matching `macros_args()` schema
(`jetengine-listings-macros` macros-2/macros-3) — both folded into their `SKILL.md`s.

Key technique this round, worth carrying forward: several claims that looked like they'd
need a real form submission (JetFormBuilder's `Action_Exception`/`Status_Info` success
wiring, the "Call Hook" action's exact hook signatures) turned out to be directly
testable by instantiating/calling the relevant classes straight from the REST callback —
`Action_Exception` is fully self-contained, and `Call_Hook_Action::do_action()` has a
public `$settings` property so it can be invoked with a fake `$request` array with no
live form needed at all. Similarly, `jetengine-listings-macros` didn't need a real
listing grid — `jet_engine()->listings->macros->handler` (a `Crocoblock\Macros_Handler`)
is directly callable. Reserve "needs a real submission/render" for claims that actually
depend on the full request lifecycle. See `HANDOFF.md`'s "Adding a new Crocoblock plugin"
section for the write-up of this as a reusable lesson.
