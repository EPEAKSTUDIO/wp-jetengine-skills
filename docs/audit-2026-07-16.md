# Repo audit — 2026-07-16

Full audit of skill coverage vs. the actual plugin source in `plugins/` and the live
JetEngine MCP server on `jackfruit.epeak.studio`. Goal: find what's missing, verify one
high-value gap end-to-end, and leave a prioritized backlog for what's left.

## Open Skills / Agent Skills standard compliance

The user's "Open Skills standard (Vercel)" question resolved to: Vercel's `skills.sh`
ecosystem is built on **Anthropic's open Agent Skills format**, specified at
[agentskills.io](https://agentskills.io/specification) — not an independent
Vercel-authored spec. Checked every `SKILL.md` in this repo against the real constraints:

| Constraint | Result |
|---|---|
| `name`: ≤64 chars, lowercase+hyphens, no leading/trailing/double hyphen, matches parent dir | **Pass** — all 8 skills |
| `description`: 1–1024 chars | **Pass** — longest is 535 chars (`jetengine-cct-internals`) |
| Body ≤500 lines (recommended) | **Pass** — longest is 151 lines |
| `license`/`metadata` field shapes (metadata = string→string map) | **Pass** |
| Directory structure (`scripts/`, `references/`, `assets/` optional) | N/A — no skill here uses these yet; all detail lives directly in `SKILL.md` + `TEST-REGIMEN.md`, which is allowed but not the spec's suggested "push detail to references/" pattern |

No changes needed for compliance. One low-cost improvement available but not applied:
the optional `compatibility` field (max 500 chars, "environment requirements") isn't set
on any skill — could add something like `compatibility: Requires shell/file access to
WordPress plugin source and a WP REST-capable sandbox for live verification` to flag that
these skills assume filesystem + HTTP access, not just chat. Left as a backlog item since
"most skills do not need it" per the spec itself.

## Gap analysis by plugin (source directories with no skill coverage)

### JetEngine (`plugins/jet-engine/includes/`) — largest gap surface

Covered: `components/{relations,listings,query-builder{mcp only}}`,
`modules/custom-content-types` (partial, read-side only), `core/mcp-tools`.

**Not covered, roughly by priority (developer-facing impact, not just size):**

1. **Query Builder itself** (`components/query-builder/` minus the `mcp/` subfolder) —
   the 10 real `sql`/`posts` queries live on jackfruit prove this is core to how
   JetEngine sites actually expose data to REST/automations (Make/Integromat-style
   `api_endpoint: true` queries with `api_namespace`/`api_path`/`api_schema`). No skill
   documents: the `%query_var|x%` / `%query_results|N|ids|field%` dynamic-arg macro
   syntax seen live in every query's `__dynamic_sql`/`__dynamic_posts` block, how
   `avoid_duplicates` / `cache_query` / `cache_expires` work, or how a query becomes a
   public REST endpoint (`api_access: 'role'|...`, `api_access_cap`). **Highest-value
   next skill** — there's a `jetengine-query-builder` gap directly adjacent to the new
   `jetengine-mcp-tools` skill and easy to verify against the 10 live queries already
   on the sandbox.
2. **Options Pages, Meta Boxes admin-UI internals (write side)** — `cct-internals`
   only covers *reading* CCT/relation data; nothing covers building meta boxes/options
   pages by hand (as opposed to via the new MCP tool). Now partially bridged by
   `jetengine-mcp-tools`, but raw-PHP registration (`Jet_Engine_Meta_Boxes`) is untouched.
3. **JetEngine's own REST API** (`includes/rest-api/`, `modules/rest-api-listings`) —
   distinct from the *custom* endpoints built in `cct-internals`; this is the
   plugin's built-in default CPT/CCT REST exposure and the "Rest API Listings" module
   (consuming *external* REST APIs as a listing source, plus its Woo-notification
   feature) — neither traced.
4. **Dynamic Visibility** (`modules/dynamic-visibility`) — Elementor/Bricks widget
   conditional-display rules keyed off meta/role/query. Common source of "why is this
   widget hidden" bug reports.
5. **Data Stores** (`modules/data-stores`) — wishlist/favorites/bookmark storage API,
   commonly chained with front-end forms.
6. **Profile Builder, Calendar, Maps Listings, QR Code, Gallery modules** — smaller,
   more self-contained integrations; lower priority unless a specific task needs one.
7. **Legacy "Forms (Legacy)" module** (`modules/forms`) — deprecated per JetEngine's own
   module description ("would be updated only for critical bug fixes... proceed to
   JetFormBuilder") — deliberately **not** recommending a skill here; `jetformbuilder-*`
   already covers the maintained path.
8. **Glossaries** (`components/glossaries`) — now partially covered by
   `jetengine-mcp-tools` (the `tool-add-glossary` MCP tool), but the "smart" (non-manual)
   glossary sources (post-type-as-glossary, taxonomy-as-glossary, etc. — `data.php`) are
   untouched; the MCP tool only supports `source: manual`.

## Follow-up round: the write-side API gap (same day, second pass)

The user flagged the actual motivating problem for this whole repo: agents hallucinating
JetEngine function names for **creating relations, updating relations, and updating CCT
data** — precisely the write side, which the first pass of this audit hadn't covered
(everything shipped so far, including `jetengine-cct-internals` and `jetengine-relations`,
was read-only: `get_parents`/`get_children`, raw `$wpdb` reads). Traced and live-verified
the real write APIs, which did not exist in any skill before this:

- **CCT row CRUD**: `Item_Handler::update_item( $itemarr )` (insert if no `_ID` key,
  update if present, one method for both) and `Item_Handler::raw_delete_item( $id )`
  — obtained via `Module::instance()->manager->get_content_types( $slug )->get_item_handler()`.
  Added to `jetengine-cct-internals` (which also gained its first `TEST-REGIMEN.md`).
- **Relation link CRUD**: `Relation::update( $parent_id, $child_id )` (create or move a
  link, idempotent, auto-creates the main DB table on first use) and
  `Relation::delete_rows( $parent_id, $child_id )` (remove a link). Added to
  `jetengine-relations`.
- **A real, previously-unknown gotcha**: `Relation::update_meta()`/`delete_meta()`
  write to a *separate* per-relation `_meta` table that, unlike the main link table,
  is **not** auto-created — calling `update_meta()` on a relation that's never had a
  meta table created silently no-ops (no error, `get_meta()` just returns `false`
  forever after). Confirmed live via direct `SHOW TABLES` check. This is exactly the
  kind of "looks right, silently doesn't work" trap that causes agents to write code
  that appears to succeed but doesn't.

All of this was live-verified, not just source-read: created a real CCT row (insert +
update + delete), a real relation (id 17, created via the same internal `Data` CRUD the
admin UI and MCP tools use — no admin UI or MCP relation tool needed), linked/unlinked
it, and reproduced the meta-table gotcha on purpose. Two more probe snippets (ids 20, 21)
kept and documented per the same convention as before.

This also **unblocked** the `jetengine-relations` `TEST-REGIMEN.md`, which had been
stuck since 2026-07-15 on "no relation exists on this site and no MCP tool creates one" —
turns out a relation doesn't need the admin UI or an MCP tool either, same as CCT/CPT/
taxonomy: the internal `Data::create_item(false)` CRUD works directly.

**Remaining known write-side gaps** (not yet covered, candidates for next pass):
CPT/taxonomy row-level writes (`wp_insert_post`/`wp_update_post` themselves are core WP,
not JetEngine-specific, so likely lower priority — but JetEngine's own meta-box field
read/write helpers for CPTs, if any exist beyond core `get_post_meta`, weren't checked),
and whether there's a JetEngine-level "set_field_value" abstraction that other Crocoblock
plugins call instead of raw meta functions (unconfirmed either way — worth a targeted
grep for `jet_engine()->meta_boxes` field-value helpers in a future pass, since that's
exactly the shape of function an agent might guess wrong).
